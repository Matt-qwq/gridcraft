# File-format parity

> **Last reviewed:** 2026-10-30 · **Last updated:** 2026-10-30 · **Change:** minor (`.xls` import reads data validation, conditional formats (the cell-value and formula rules), hyperlinks and frozen panes, spec-derived and fixture-tested only; `CF12` colour scales, data bars and icon sets are refused with a warning, and BIFF5 stays refused because [MS-XLS] specifies BIFF8 only. Every format Excel opens or saves, with GridCraft's read and write support, fidelity and tests.
Part of [target-app-parity.md](target-app-parity.md). **File formats: ~50% ready, 80–120 h**
(estimated).

Excel's list comes from Microsoft's public "File formats that are supported in Excel"
documentation (the Office bundle is off limits under this repo's clean-room rule). GridCraft's
support comes from `crates/engine/src/io.rs` (`FileKind`), `crates/xlsx/src` and the tests in
`crates/xlsx/src/tests/` (round-trip, fixtures, malformed input, CSV, ODS, XLSB, XLS, PivotTables).

Legacy scalar `INDEX(range, MATCH(...))` formulas remain ordinary formulas on save, including when
shared formulas are expanded during import (`array_export.rs`, #1505).

## Workbook formats

XLSX column declarations are limited to 1,000,000 expanded column assignments per worksheet,
including repeated overlaps across `<cols>` blocks. Spans are clipped to the grid and records
that would be skipped as defaults are excluded before charging the limit. Excess work returns
the existing file-too-large error; accepted overlaps retain their existing last-wins behavior
(#1022).

Ink created with Draw is written as standard, unfilled DrawingML polylines, without visible point
captions or private metadata. Supported numeric polylines reopen as editable ink, retaining points,
colour, integer width and anchor. Curves, filled paths, transforms and unsupported line styles are
not interpreted as ink. This does not implement Office InkML or fix inserted icons (#551).
Command and package tests cover repeated saves and unrelated cell edits; external Excel rendering
and repair-free opening remain unverified.

Dynamic-array formulas keep their mark on save. A formula read with dynamic-array cell metadata
(`cm`, the `XLDAPR` record in `xl/metadata.xml`) is written back with it, together with the
metadata part, even when it returns one value and GridCraft's own shape analysis would not need
array evaluation. Dropping the mark turned such formulas into legacy ones, which Excel evaluates
with implicit intersection: `SUMPRODUCT(IFERROR(B1:B3/C1:C3,0))` recalculated to a different
value in Excel. Moving the formula, inserting or deleting rows and columns, and renaming sheets or
names keep the mark; retyping the formula drops it, and the writer then decides from the
formula's shape. Rich-value metadata other than cell pictures (data types, `#SPILL!` error
values) is still dropped.

## Pass-through of unmodelled XLSX content

Opening a workbook and saving it must not simplify it. `crates/xlsx/src/passthrough.rs` keeps the
parts GridCraft has no model for as they are — bytes, relationships, content type — and writes them
back where they were read from. It is the same mechanism for every row of the matrix below: a
relationship graph walked from an owner, refused when it reaches content GridCraft rewrites.

| Content | Kept | Owner | Notes |
|---|---|---|---|
| Custom document properties, ribbon customisation and add-in task panes | part bytes, relationships, content types | package root | custom UI parts are renamed only when they would collide |
| Custom XML (items, properties, XML maps) | same | workbook | bindings are kept; mapped cells are not adjusted |
| Links to external workbooks | same, never followed or refreshed | workbook | `[1]` in formulas is the position in `<externalReferences>`; relative paths are rebased on Save As |
| Data connections | same | workbook | |
| Sheet query tables, table-attached query tables | same | worksheet, table | a table's query table is written as the table part's own relationship, so it leaves with the table |
| Printer settings | same | worksheet (`<pageSetup r:id>`) | #324 |
| Form controls, ActiveX controls, OLE objects, sheet backgrounds | same, with their VML shapes | worksheet | not shown or editable; notes keep the shape blocks they use |
| Pictures in headers and footers (`&G`) | same | worksheet (`<legacyDrawingHF>`) | not shown; #1257 |
| Chart sheets | same (sheet, drawing, chart, style, colour) | workbook | #727; left out when a sheet they plot was deleted or renamed, or a worksheet took their name |
| Slicers and slicer caches | modelled for a plain tabular cache; anything else same (byte-identical) | workbook and PivotTable | a modelled slicer's name, caption, style, column count, item list and selected tiles are read and written (`crates/xlsx/src/slicer.rs`, `slicer_tests.rs`); a modelled one is written from the model and never also kept, and goes when its PivotTable is deleted or renamed; an OLAP cache, item properties, unknown attributes or a damaged part stay on the pass-through path (not editable) |
| Timelines and timeline caches | modelled for a plain cache with no selected date range; anything else same | worksheet and workbook | name, caption, style and time unit (`level`) are modelled and written; a selected date range is not modelled yet, so such a timeline stays on the pass-through path; the on-sheet drawing shape is not written (the model keeps its anchor) |
| Unmodelled `extLst` children | the `<ext>` element, with its relationship ids rewritten | workbook, worksheet, table, PivotTable, pivot cache definition | the extensions GridCraft writes itself (calc features, data bars, sparklines, x14 validations, the PivotTable's own x14 extensions) are written from the model, never kept from the source |
| **Dropped: the data model** (Power Pivot `xl/model/…`, `powerPivotData`) | — | — | the parts and the connection they hang off cannot be verified without modelling OLAP sources |
| **Dropped: chart `extLst` children and chart details** | — | — | the chart model and its writer belong to gap #4; a chart part has no stable identity (name or id) to hang a fragment on |
| **Dropped: anything whose graph reaches rewritten content** | — | — | e.g. a control whose preview image is a chart part: keeping it would point at a part GridCraft rewrites |
| **Dropped: Strict Open XML content** | — | — | its namespaces differ from what GridCraft writes |

Rules that keep a save safe:

- **Byte-identical parts.** A kept part is written from its original bytes; only its relationships
  are re-serialised (ids unchanged, targets renamed when a part had to move). `[Content_Types].xml`
  gets an `Override` per kept part (or the original `Default`) from the source file.
- **No dangling reference.** Kept extras hang off their owner's name (a table's `name`, a
  PivotTable's `name`) or live on the sheet itself. A deleted sheet takes its content; a deleted or
  renamed table or PivotTable takes its extras, the parts only they reach, and the extension that
  named them. A slicer or timeline whose cache is gone goes too, and a slicer cache that names a
  PivotTable the workbook no longer has is dropped with its slicers. Relationships are only written
  for parts that are written, so a dropped part never leaves an `r:id` behind: a fragment whose ids
  can't all be resolved is dropped whole.
- **Modelled owners are written once.** A slicer or timeline the model understands is written from
  the model and removed from the kept content on read (its workbook/PivotTable/sheet extension and
  the relationships only it used), so no part or `<ext>` is written twice; a kind is modelled
  all-or-nothing, so one cache GridCraft cannot fully understand leaves every slicer (or timeline)
  of that workbook on the kept path. The source extension is dropped only when the model rewrites
  it, which is what keeps an open → save from duplicating a slicer cache reference.
- **Bounded.** 256 MiB kept per workbook, 64 MiB per part, 4,096 parts, 4 MiB per XML fragment,
  8 MiB of `extLst` children per owner, 256 elements of nesting; a part over its limit is
  dropped with a warning instead of failing the read.
- **Validated.** `testing::check_package` (run by `write_xlsx` on every package the test suite
  saves, up to 8 MiB) proves the result: every relationship target exists, every part has a
  content type, no part is orphaned, and there is no stale content-type override. `owner_extensions.rs` (slicers,
  timelines, table query tables, owner `extLst` children) and the deletion and rename tests drive
  the drop rules.

**Not verified:** an Excel run over a workbook with slicers or timelines saved by GridCraft; repair
prompts remain unknown (gap #1).

## Import sources (Get & Transform)

Excel's Get Data reaches files (Excel, CSV, XML, JSON, PDF, Parquet, folders), databases (SQL
Server, Access, ODBC, …), web pages, SharePoint and online services, through Power Query.
GridCraft imports CSV/TSV, JSON and HTML tables only, with no query editor, no connections and no
refresh. Counted under features (Get & Transform, ~10% ready), not here.
